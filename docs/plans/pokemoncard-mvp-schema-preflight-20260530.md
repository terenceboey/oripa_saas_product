## Safe next-step migration policy

Until this preflight is resolved, the safe policy is:

1. Do not run auto-generated Prisma migrations against the configured Render DB.
2. Do not run `npm run db:migrate` (`prisma migrate dev`) against `.env` as currently configured.
3. Do not run the manual `prisma/sql/catalogitem-*.sql` files against live as-is; they are incomplete and do not reconcile live-only schema.
4. First update repo Prisma schema or a separate audited SQL baseline to model/preserve live objects:
   - `CatalogSet`
   - `CatalogItem.catalogSetId` relation and index
   - canonical catalog tables currently present live, or an explicit retention/drop decision with backup and approval
   - live storefront/vendor/pack image columns, or explicit retention/drop decision with approval
   - existing `pg_trgm` extension and `CatalogItem_lower_name_trgm_idx` as an SQL-managed object
5. Generate migration SQL only as a review artifact first, never directly applying it.
6. Split migrations by concern:
   - schema reconciliation/no-op preservation baseline;
   - additive search indexes/query-support columns;
   - additive `PackPrize` snapshot columns;
   - publish/freeze fields;
   - inventory foundation.
7. For live managed Postgres, prefer additive/idempotent SQL with `CREATE INDEX CONCURRENTLY` for new large-table indexes, and avoid wrapping concurrent index creation in a transaction.
8. Any destructive operation requires explicit operator approval, named backup/snapshot, row counts before/after, and rollback instructions.
9. For local development, create a separate local `DATABASE_URL` before running migrations. The current `.env` points at Render, not localhost.
